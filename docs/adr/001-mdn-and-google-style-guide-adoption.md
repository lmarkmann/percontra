# ADR 001: MDN and Google Style Guide Adoption

**Status:** Accepted
**Date:** 2026-07-11
**Deciders:** Luis Markmann

## Context

Two external style guides were evaluated against this template: Mozilla/MDN's JavaScript code-example guidelines and Google's TypeScript Style Guide. The goal was not wholesale adoption but a complete, auditable classification: which conventions are already enforced here, which are worth wiring up, which belong as written conventions, and which to reject with a reason.

Ground rules for the evaluation:

- **TypeScript-first weighting.** This is a TS codebase; where Mozilla and Google genuinely conflict on a language point, Google's TS guidance wins by default. Exceptions are called out in Contradictions below.
- **Angular lens on Google.** Google's guide is written for an Angular codebase. Every Google rule was tested for being a general TypeScript rule versus an Angular idiom leaking through; Angular-specific rules were dropped (see Angular-lens exclusions).
- **No Prettier.** Formatting is owned by oxfmt (import sort, Tailwind class sort, Prettier-conformant output), linting by oxlint, types by tsc strict. Rules that exist only because a guide assumes Prettier, and rules purely about writing teaching snippets for docs, were skipped as such.
- **Grounded in current tooling docs**, not guide-era assumptions: tsc 7.0.2 (the native compiler; TypeScript 6.0 semantics, so `strict` is the default and `esModuleInterop`/`alwaysStrict` cannot be disabled), oxlint 1.73.0 (rule ids and default categories verified against the installed configuration schema and the oxc.rs rules index), oxfmt 0.58.0 (passes 100% of Prettier's JS/TS conformance tests, so "Prettier normalizes this" claims transfer to oxfmt).

Three existing decisions do a lot of silent work and are cited repeatedly in the table:

1. `tsconfig.base.json` already sets `strict`, `verbatimModuleSyntax`, `erasableSyntaxOnly` (bans enums, namespaces, and parameter properties outright), `noFallthroughCasesInSwitch`, `noUncheckedIndexedAccess`, `noImplicitReturns`, `noImplicitOverride`.
2. `.oxlintrc.json` enables the `correctness` and `suspicious` categories as errors with `typeAware: true`, which already switches on many rules the guides ask for (each named in the table with its category).
3. ADR 025 established the pattern this ADR extends: the `pedantic`, `style`, and `restriction` categories stay off wholesale, and individual rules are pulled out as explicit single-rule opt-ins.

Every adopted rule below was dry-run against the full tree before adoption, so the churn column of the Consequences section is measured, not estimated. Rules that do not exist in oxlint 1.73 are stated as such rather than invented: `one-var`, `camelcase`/`naming-convention`, `no-restricted-syntax`, `new-parens`, `no-invalid-this`.

## Rule identifiers

Adopted and classified conventions get stable local ids: `JS-nn` for Mozilla rows, `GT-nn` for Google rows, both in guide order. These ids are referenceable from code comments, reviews, and future ADRs, and are never renumbered or reused. Where both guides state the same convention, the Google row cross-references the Mozilla row.

Verdicts: **Enforced** (already covered; mechanism named), **Tool** (adopt via a named oxlint rule or existing tool setting), **Convention** (adopt as a written rule in `.claude/CLAUDE.md`; no tool can enforce it), **Skip** (with a one-clause reason).

## Angular-lens exclusions

Google rules dropped as Angular (or Google-internal) idioms rather than TypeScript-language guidance:

- **Decorators (GT-71, GT-113).** "Use only framework decorators" presumes Angular's `@Component`/`@NgModule`. No decorator framework exists here, and the guide's own rationale (experimental decorators diverged from TC39) argues for having none.
- **Parameter properties (GT-29).** Ergonomics for Angular constructor injection. This repo bans them outright via `erasableSyntaxOnly`, the opposite decision, taken for type-stripping compatibility.
- **Template-used property visibility (GT-31).** "Use `protected` for Angular template properties" has no meaning without string templates; React props are plain function parameters.
- **`#private` field ban (GT-27).** Motivated by down-level emit size for Angular's browser matrix; at a native ES2023 target the penalty does not exist.
- **Event-handler uninstall patterns (GT-42).** addEventListener/removeEventListener identity bookkeeping for framework DOM code; React's synthetic event system and effect cleanup make the prescription inapplicable.
- **Apps JSPB proto imports.** Google-internal build-system rule; no row assigned.
- **`@NgModule` doc-comment exemption (part of GT-110).** Angular tooling artifact.
- **Conformance frameworks (GT-106).** tsetse/tsec are Google-internal; the closest analogue here is the oxlint category config plus tsc strict.

## Contradictions resolved

Genuine Mozilla-vs-Google conflicts and which won:

- **(a) Braces on control flow (JS-18 vs GT-55).** Mozilla: always brace. Google: single-line `if` may elide. Google wins (TS-first): `curly` at `"multi-line"`. Measured consequence: the 80 existing single-line guard clauses stay legal; any body that wraps must brace.
- **(b) Arrow body style (JS-13 vs GT-39).** Mozilla prefers implicit returns wherever possible; Google requires a block body when the return value is unused, to avoid leaking values into `void` positions. Google wins: no `arrow-body-style` rule, and the leak is guarded by the already-active `typescript/no-confusing-void-expression` (its `ignoreArrowShorthand: true` is a deliberate local exception, kept).
- **(c) `hasOwnProperty` (JS-28 vs GT-21).** Google's guide still demonstrates `Object.prototype.hasOwnProperty` filtering; Mozilla mandates `Object.hasOwn()`. Mozilla wins: this is platform recency (Baseline ES2022), not a live TS-language position; Google's examples simply predate the API.
- **(d) Arrows assigned to identifiers (JS-12 vs GT-37/38).** Mozilla says avoid assigning arrows to identifiers at all; Google allows `const`-assigned arrows for nested functions and requires arrows over function expressions. Google wins: the convention line requires declarations only for top-level named functions and blesses const-arrow locals and callbacks.
- **(e) String quotes (GT-47).** Google mandates single quotes; MDN delegates to Prettier (double). Resolved by constraint rather than preference: formatting belongs to oxfmt, whose config keeps double quotes. No rule adopted from either side.

## Decision

Adopt the **Tool** rows as single-rule opt-ins in `.oxlintrc.json` (the ADR 025 pattern; the pedantic/style/restriction categories stay off wholesale), and the **Convention** rows as a Code conventions section in `.claude/CLAUDE.md` referencing this ADR. Everything already enforced stays where it is; nothing is double-encoded as both a lint rule and a CLAUDE.md line.

## Consequences

### `.oxlintrc.json` additions

New eslint rules, all error: `no-alert`, `no-array-constructor`, `no-case-declarations`, `curly` (`"multi-line"`), `default-case-last`, `guard-for-in`, `no-else-return`, `no-empty`, `no-implicit-coercion` (allow `!!`), `no-multi-assign`, `no-new-func`, `no-new-wrappers`, `no-object-constructor`, `no-proto`, `no-prototype-builtins`, `no-restricted-globals` (`parseInt`, `parseFloat`), `no-throw-literal`, `no-var`, `object-shorthand`, `prefer-arrow-callback`, `prefer-const`, `prefer-object-has-own`, `prefer-rest-params`, `prefer-spread`, `prefer-template`.

New typescript rules: `array-type` (array-simple), `ban-ts-comment`, `dot-notation`, `no-empty-object-type`, `no-inferrable-types`, `no-require-imports`, `prefer-for-of`, `prefer-promise-reject-errors`, `switch-exhaustiveness-check` (default counts for unions), all error; `prefer-readonly` warn.

New unicorn rules, all error: `no-static-only-class`, `number-literal-case`, `prefer-optional-catch-binding`, `throw-new-error`.

New import rules, both error: `no-default-export`, `no-mutable-exports`.

New overrides: `**/*.cjs` turns off `typescript/no-require-imports` (`lighthouserc.cjs` is legitimately CommonJS); the four default-export contract files turn off `import/no-default-export`.

### `.claude/CLAUDE.md` additions

A Code conventions section carrying the Convention rows verbatim (casing table, declaration-vs-arrow split, comment split, non-null-assertion justification, literal annotation over `as`, optionality style, `Number()` parsing discipline, `Map`/`Set` over index signatures, catch discipline).

### Code changes at adoption

- `src/test/state-matrix.ts`: two trivially inferred `RegExp` parameter annotations dropped (GT-90).
- Everything else adopted at zero churn; measured by dry-running every rule against the full tree before adoption. Notably `switch-exhaustiveness-check` initially flagged the `demoView` switch in `src/contract/dashboard-fixtures.ts` for an unmatched `null`; with `considerDefaultExhaustiveForUnions: true` its existing `default` group satisfies the rule, which is precisely Google's "switch must have a default" contract.

## Alternatives considered

### Enable the pedantic/style/restriction categories wholesale

Would cover most adopted rules in three lines. Rejected: re-litigates ADR 025's finding that those categories drag in noise (`prefer-readonly-parameter-types`, `no-array-reduce`, filename casing); explicit opt-ins keep every active rule a deliberate decision.

### Adopt Google's interface-over-type-alias rule (GT-96)

Rejected. The repo has 81 object-shaped type aliases against 9 interfaces; converting is churn without a payoff since TS 7's native checker erased the display/perf argument the guide cites, and interface declaration merging is a footgun in application code. Enforcing the opposite (`consistent-type-definitions: "type"`) under a Google-adoption ADR would misrepresent the source; neither direction is enforced.

### Adopt `typescript/only-throw-error` for GT-61

Rejected: TanStack Router's `beforeLoad` contract throws `redirect()` objects by design; the rule would need a permanent disable at every auth boundary. `no-throw-literal` plus `prefer-promise-reject-errors` capture the real hazard (throwing strings and rejecting with non-Errors).

## Validation

`pnpm lint`, `pnpm typecheck`, and `pnpm test` pass after adoption with the two code fixes above. Each adopted rule was verified live by dry-run before merging (violation counts per rule recorded above); spot-checking `const a = new Array(2)` in a component produces an `eslint(no-array-constructor)` error.
