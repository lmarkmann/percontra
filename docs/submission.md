# Submission checklist (product track)

Source: `YlookupEncodeHackathon.pdf`, slides "Product track scoring", "How to submit", "Rules", "Credits & tooling".
Every requirement below is quoted from the deck. Nothing here is inferred.

## Deadline

> Deadline Sunday 12:00. Submit early, resubmit if you need to.
> 12:00 Submissions close. Tally form shuts, repos are frozen

## The three deliverables

### 01 Tally form
> One submission per team, through the Tally form we share at team-forming. Link also pinned in the event channel.

- [ ] Link obtained (Discord event channel pinned message, or front desk). Not present in any file we were given.
- [ ] Submitted once, by: ____
- [ ] Resubmitted if repo or video changed after first submission

### 02 Public GitHub repo
> Public at submission — the code review is scored from it. At minimum it must run from a script: README plus one command we can execute.

- [ ] Repo public before 12:00 Sunday
- [ ] README present
- [ ] One command that runs it (our `just demo` wrapping `./scripts/demo.sh`; both listed in README)
- [ ] No API key in the repo. From "Credits & tooling": *"One key per team. Do not commit it to your public repo — judges will notice."*
- [ ] Built this weekend. From "Rules": *"We encourage something built fresh this weekend. Boilerplate and open-source libraries are fine — an existing project is not."*
- [ ] We can defend the architecture. From "Rules": *"Use whatever helps. You still own the architecture — code review assumes you can defend it."*

### 03 Demo video
> 3–5 min demo video. Open with the problem you picked and the interview it came from. Then show the product working.

- [ ] Length between 3 and 5 minutes
- [ ] Opens with the problem and names the interview (file name and the quote)
- [ ] Shows the product working
- [ ] Uploaded and link ready for the Tally form

### Optional
> Hosting is optional, but it earns extra points.

- [ ] Hosted URL: ____

## What it is scored on (25% each)

> Problem identification — Did you find a real problem in the interviews — and can you show us where it came from?
> Product — Does what you built actually solve the problem you chose to tackle?
> UI — Clean and considered. A non-technical fund manager is the user. No AI slop.
> Code review — Structure and style a working team could live with. Reviewed on submission.

## Team rules

> Solo, or up to 4. One track per team. Declare it when you form. Switching after 13:00 Saturday is not practical.

- [ ] Team declared as product track: ____
- [ ] Team name (same as product name unless decided otherwise): ____
